## Executive summary

Target: latest fetched `main`, **2bcd8edf045b38c1b02437f7672178b42991ac07**,
reviewed on 2026-10-13. This is a documentation-only assessment. No agent production
changes, Rust tests, benchmark code, reference C# source, or integration fixes are
included in this commit. The earlier integration task was superseded; its unfinished
changes remain in a separate checkout and are not evidence of fixes on main.

The canonical SECA-Light engine has credible evidence for selective reconstruction,
stable vocabulary, gamma forgetting and transactional failure isolation. It does
**not** have demonstrated scientific or executed C# parity. Two immediate engineering
problems are established on clean main: CSV row identities discard distinct articles
across files, and snapshot restoration accepts certain corrupt or expired state.
Timestamp conversion is also unimplemented. Shared-word metrics and several
construction/admission interpretations remain scientifically unresolved.

Register: **15 findings: 0 Critical, 4 High, 8 Medium, 3 Low**. Severity reflects
potential consequences; confidence separately reflects evidence. Do not present
this audit as production approval or full validation success. Prioritize ingestion
and snapshot reliability, then settle scientific questions with deterministic fixtures
before changing algorithmic behavior.

## Scientific fidelity

Evidence hierarchy: published [SECA paper](https://doi.org/10.1109/ACCESS.2023.3331219)
→ scientific specification → original C# reference → Rust implementation.
The [accepted author manuscript](https://www.researchgate.net/publication/375503068_Real-Time_Event_Detection_Using_Self-Evolving_Contextual_Analysis_SECA_Approach)
was read, especially V, VII-A/Figure 3, VII-B equations 2–12, VII-C. The university
portal's final published PDF was inaccessible (401); final-PDF equivalence is not
asserted. Paper source sets and old-word error sums guide assessment; the C# code
is a behavioral reference, not an unquestioned scientific oracle.

No `dotnet`, `mono`, `mcs`, `csc` or `msbuild` was available. The original project
is .NET Framework 4.7.2/Windows Forms with additional dependencies. **Every C#
comparison is static**, including predictions conditional on collection order.
Neither parity agent supplied executed C# golden outputs.

Verified Rust invariants and static correspondence support top-down scope delivery,
multiple ordinary-node source matches, ancestor exclusion during replacement,
disjoint reconstruction targets and fresh IDs. The 11 clean-main HKT tests prove
the specified Rust cases, including known divergences; they do not prove C# parity
or reproduce the published event-detection evaluation.

Rust transactional failure behavior, deterministic IDs, distinct-source counts,
full precision and coherent node creation are defensible differences. C# swallowed
exceptions, mutable parallel frequency rows and stale dynamic candidates are risks
in the reference itself. Reproducing those behaviors is not recommended.

## Correctness and state integrity

See [engineering evidence](audit-engineering-evidence-2026-10.md) for commands,
fixture provenance, exact test names and clean-main CLI reproduction.

**Confirmed current defects:** two independently converted one-row CSVs with
*different URLs* both get `row_000001`; initialization processes one source and
restored batch 1 processes **zero** sources. A valid UTC timestamp becomes null.
Snapshot tests demonstrate acceptance of unknown expected/top/membership word IDs
and evidence older than gamma. These are pre-existing main defects newly confirmed
by consolidation, not regressions introduced by audit documentation.

The unchanged state-agent suite passed **14/18** against clean main. Passing cases
cover cache/root/attachment integrity, ordinary descriptor IDs, source memberships,
identity/provenance agreement, allocator bounds, schema rejection, duplicate handling,
expired identity readmission, vocabulary persistence, repeated reconstruction,
JSON restart equivalence and failure isolation. Four deliberately corrupt restore
cases failed because corrupted state was accepted. Normal forgetting works in the
executed scenarios; restore does not enforce the same retention boundary.

The CSV agent implemented a proposed correction in its branch. Its workflow tests
passed on that changed integration checkout, not on clean main. URL-less IDs use
conversion UUIDs, so saved JSON has stable identities but reconversion does not
recognize the same anonymous article. URL aliases and lifetime deduplication remain
application policy questions. The audit neither integrates nor endorses this scheme
as a complete production ingestion policy.

Snapshot filesystem commit uses fsync/atomic rename in CLI `update.rs`; tree/report
outputs are not a multi-file transaction. Concurrent writers require coordination
according to [state.md](state.md). Those are documented limitations, not demonstrated
crash or concurrent-writer failures. Further corruption coverage remains necessary;
passing fixtures do not establish exhaustive validation.

At 400 sources, novel gamma=3/30 updates reached **1283.30 ms median**, **1931.66 ms

## Prioritized recommendations

1. **Scientific correctness:** establish shared-word aggregation (F05), W0 (F06)
   and candidate eligibility scope (F07); then resolve recursive CA construction,
   branch boundary and greedy ties (F08/F09/F11). Keep paper rules above C# quirks.
   Record original-runtime golden fixtures and precision boundaries (F10/F12).
2. **Production reliability:** correct CSV identities before trusting persistent
   CSV streams (F01); enforce missing snapshot checks (F03/F04), retaining the
   failing assertions; specify timestamp policy (F02). Complete full validation
   (F15), malformed-state coverage and application crash/concurrency experiments.
3. **Performance:** profile final-tree diagnostics and reconstruction/topology
   growth under real deployment parameters (F14); measure durable persistence;
   run longer novel streams and budget append-only vocabulary (F13). Use repeated
   idle-host trials before declaring latency regressions or making an SLO.
4. **Optional improvements:** document URL canonicalization, anonymous reconversion
   replay and lifetime deduplication policy; retain portable benchmark artifacts;
   automate fixture provenance/normalization. Avoid copying C# archives, fallback
   paths, policy scaffolding or swallowed exceptions into the engine.

These are recommendations only; none is implemented by this audit.

## Remaining uncertainties

- Which contextual frequency represents a descriptor adopted by multiple nodes?
- Are persistent unassigned expected words old vocabulary on later updates?
- Which historical memberships contribute to candidate beta, and is the denominator
  the node union or its prominent word's sources?
- Does original CA allow sibling-descriptor reuse in descendants? What tie and
  minimum-branch policies are scientifically intended?
- Does the final published PDF materially differ from the inspected manuscript?
- How does the unmodified C# implementation actually enumerate ties, handle stale
  expectations/shared keys, and behave under concurrent mutable branch frequencies?
- What is the intended empty reconstruction outcome, and is the internal no-record
  skip reachable through real inputs? Rust versus C# failure behavior is static here.
- Can deployment workloads meet a defined processing-plus-ingestion-plus-durable-write
  deadline with default branching and thresholds? What happens beyond 90 novel batches?
- How does persistence behave under crashes and concurrent writers? No fault-injection
  or durability latency campaign was performed.
